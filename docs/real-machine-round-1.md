## 发现 1：ack「在呢」后的小杂音（已修，属于我们 adapter）

- ack 490 ms = 11 个 42.7 ms 设备周期 + **20.7 ms 尾巴**；
- 旧逻辑：EOS 在最后整周期后 1.2 s 才触发，把 20.7 ms 尾巴补成整周期**在 1.2 s 后才发**；
  设备因此开了一个 `periods=1、primeWait≈1242 ms` 的幽灵流（16:23 的设备日志），起始突入 = 听到的"小杂音"；
- 修复（`adapter._eos_after_idle`）：**EOS 时丢弃 <30 ms 的尾巴**（人耳不可闻）；更长的尾巴加 10 ms 淡入 + 淡出、
  补齐到整周期再发（避免突入）。新增 `dsp.fade_in_pcm` 与两个单测。
- 第一版修复（丢弃尾巴）验证后又发现 9 哥听到"和'呢'一起出现"的杂音——原因是**硬切**在最后一个音节上；
- 第二版：**短流用 0.15 s 短 EOS 空闲**、尾巴淡入淡出后补齐整周期尽快发出；长流保持 1.2 s 空闲、丢弃 <30 ms 尾巴。
  9 哥复听仍有"和『呢』一起"的杂音 → 定位到**淡入**把尾巴起始做了幅度调制（尾巴本来就是同一流的延续，不需要淡入）。
- 第三版（最终，9 哥确认"没有了"）：尾巴**续在同一流里、不加淡入**，只做结尾 10 ms 淡出 + 补静音；
  客观验证：下发 PCM 衔接跳变 105（可忽略）、末样本 0；设备日志 `periods=12`、同一秒收尾，无幽灵流。

代码位置：`src/rui/audio/process.py` `_device_wake_playing()` / `_on_kws_wake`。已作为观察反馈 rui#7，等他们确认。

## 停止 / 打断的反馈设计（9 哥 2026-10-25 18:45 确认：保持现状）

两条路径，都是 rui 的设计，不是"打断没做"：

**A. 用唤醒词打断（播放中说「你好小瑞」）**

- 服务端 **16 ms** 内停推 + 清队列（实测），设备 ALSA 缓冲另约 300 ms；
- **故意不播 ack「在呢」**（避免盖住用户要说的话），LED 走 `wake → listening`；
- 之后：继续说话 → 直接进新回合；不说话 → 15 s 后播告别语（`session.farewell_text`）再熄灭。

**B. 说停止词（「停一下 / 停止 / 别说了 / 退下吧 / 再见 / 睡了…」）**

- 无音乐时走 `bare_stop`：播一句很短的确认（`STOP_REPLIES` 之一，当前「好。」）→ 关闭会话、LED 熄灭；
- 若在放音乐：`media_stop` → 「好，不放了。」→ **保持**会话（只停音乐）；
- 匹配是**整句匹配**（含最多 2 字尾），不是包含匹配——`关掉客厅灯` 这类家居命令不会被误判成停止。

**结论**：保持现状（选项 1）——打断 = 立即静音 + LED，明确"停止" = 一句「好。」+ 熄灭；不向上游提
"stop cue / 可配置 stop reply" 的 feature request。
