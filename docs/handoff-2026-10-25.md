# 交接（2026-10-25）：Dot2 桥 → rui 卫星

> 给下一个会话的完整背景。仓库：`rui-dot2-bridge`（桥/文档）、`echomuse-dot2-ref`（固件补丁）。
> 设备：Echo Dot 2（RS03QR）+ EchoMuse 自定义固件。rui 侧是谁：见各 issue。

## 一、项目背景

把一台已解锁的 Echo Dot 2 改造成 **rui 的语音卫星**：说唤醒词 → rui 出答案 → Dot 出声；播放中能打断；
断线/断电自恢复。设备端跑 EchoMuse 固件（TLS WebSocket + `X-EM-Token`，`/control` + `/data` 两通道），
rui 侧用 **adapter/插头** 顶替原 EchoMuse controller（不改 rui 源码）。

几条一以贯之的约束：

- **不改 rui 项目代码**（本地 checkout 有 9 哥自己的改动，也不动）；
- **不碰 `.168` 生产 NAS**；测试都在另一台独立服务器上；
- **开放设备尽量自己干**（AEC/唤醒等判断在设备侧，rui 定策略）；
- 部署形态从 2026-10-24 晚起改为 **Docker / 飞牛镜像管理器方式**，不再 systemd+venv；
- 下一次冷启动由**纯用户视角的智能体**照上游文档部署，Lead 只配参数。

## 二、当前成果（已验证）

1. **桥 `rui-dot2-bridge`（0.1.x 时代）**：真机跑通 wake → ASR → LLM → TTS；单声道 16k 上行、48k 下行、
   EOS/flush、LED、音量上限、原厂 EQ 阶梯 + 限幅、回滚；barge-in 实测服务端停推 3–7 ms。
2. **P3 固件补丁**：独立仓库 `echomuse-dot2-ref`（MIT，v0.1.0 release、CI、A/B 安装/回滚脚本）；
   已安装到设备 **server_b**（build `20261024-1911-dev`，基于 EchoMuse v2.19.0-ea.1），server_a 保留旧固件。
3. **AEC 结论**：该声学链路线性可消除上限 **14–18 dB**；设备 AEC 稳态 **16.5–19 dB** 已在该量级；
   生产选 **`ref_channels=0` + 设备 AEC**，2ch 参考不再必要。rui 的 0.5–9 dB 是"增量 ERLE"，不是系统 ERLE。
4. **误唤醒基线**：20 次文件播放（三档音量 + `wakeMic` 0/6）**0 误唤醒、0 空唤醒**；
   此前"自听"是 `debug/say` 会把输入文本记成 turn 造成的误判（`debug/play` 干净复测无自听）。
5. **测试实例**：rui **v0.2.2** 官方 Docker 镜像部署成功（控制台 **8080**、healthy；`devices: []`），
   密钥已配（DeepSeek / 讯飞 / 火山 `VOLC_API_KEY`），火山 ASR 实测可用（10.6 s 长句全对）。
6. **rui issue**：#1 播放空档契约（0.2 修，maintainer 已回复）；#2 Linux 部署/doctor（已修已关）；
   #3 `device_wake` 契约请求（open）；#7 0.2.2 接入契约问题（open，等回复）。

## 三、当前问题（阻塞）

- rui 0.2.2 的设备接入变成 **单入口 4412（明文 ws + query token）**，且：
  - 声明式 plug 的 loader **不执行 entrypoint**，out-of-tree adapter 只能靠 `PYTHONPATH + sitecustomize`
    非官方注入，官方镜像升级会断；
  - 一个音频面只驱动一台设备，端口内没有协议 demux；LX06（明文 ws）与 Dot2（wss + `X-EM-Token`）无法同实例共存；
  - 0.1.x 的 8095/8870/8872 在 0.2.2 全仓不存在（响度/EQ 运行时服务也没了）；
  - `oww_wake` 只有"让位"语义，没有"设备唤醒起回合"的消费端；
  - 无 per-block 播放头设备的 play-head 契约未定。
- 因此 **Dot2 现在接不上**：`controller.json` 只指向测试主机 **8870**，设备每 5 s 重试、`connection refused`
  （预期离线，不会坏）。
- **桥代码暂停迁移**，避免按旧假设写完又被 rui 接口改动推翻；AEC 归属、2ch 取舍也等 rui 回复。

## 四、下一步

1. **等 rui 答复**（#7）并定稿 plug/接口文档；文档出来后按定稿迁移桥，不提前写。
2. 迁移方向（已定的部分）：
   - Dot2 端口保持 **8870（wss）**，设备 `controller.json` 不用改；
   - **多卫星共存**：LX06 + Dot2 同时在线；唤醒后谁接管由 **rui 仲裁**，不是音箱；
   - 开放设备 **AEC 归设备**（`ref_channels=0`），2ch 仅作为可选能力保留；
   - Docker 部署：官方镜像 + 插件层（自定义镜像）或 rui 给出的官方 out-of-tree 方式。
3. 冷部署流程：**纯用户视角智能体**照上游文档用 Docker 部署 → 把它遇到的卡点报告 → Lead 配参数
   （密钥、设备、音量、AEC/wake 参数）→ 端到端回归（唤醒/打断/自听/回滚）。
4. 回归通过后：更新 `.34` 上 `devices[]`、打开设备连接、复测 barge 与多设备仲裁；把 rui 侧问题补进 issue。
