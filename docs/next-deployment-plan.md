# 下次部署计划：以"纯用户"视角的 Docker 部署

> 状态：等待 9 哥通知 rui 新版本就绪。`.34` 已清空，Dot 只指向 `.34`。

## 目标

1. 按**飞牛 Docker 镜像管理器**的方式部署（镜像 + compose，不再 systemd+venv）；
2. 由**一个全新的智能体**以"纯用户"身份完成部署：只给它上游文档/仓库，不给内部踩坑记录；
3. 智能体把**所有卡点**（文档缺失、版本不符、权限、模型下载、端口、健康检查、密钥申请等）如实报告给 Lead；
4. Lead 只做**参数配置**（token、设备端 token、音量上限、ref_channels、网关等），并从报告里挑出 rui 侧/文档侧需要修的问题。

## 为什么这样做

上一轮部署踩的坑有一半是"内部已知、但外部用户不会知道"的（ORT 库、X-Auth-Token、模型路径、A/B 安装）。
纯用户视角能验证：一个拿到仓库和文档的人，能不能独立跑起来。

## 智能体约束

- 上下文全新，**不得读取本仓库 docs 里的踩坑记录**（findings / retro / aec-*），只能读上游 README/docs 与发布说明；
- 禁止向 Lead 要"提示"，遇阻先按文档尝试，失败则记录并继续下一步；
- 只读/只写 `.34` 与它自己的临时目录；**不碰 `.168`、不碰 Mac 实例、不改设备固件**；
- 报告不得包含明文密钥/IP 之外的部署细节（按 9 哥的保密要求，文档里用占位符）。

## 智能体产出

1. 实际执行的完整命令序列 + 每步结果；
2. 问题清单，按 **阻塞 / 严重 / 一般 / 文档瑕疵** 分级，附原始报错；
3. 最终是否跑到 `health speaker_connected=true` + 一次 TTS + 一次唤醒；
4. 需要 Lead 配置的参数清单（不含值）。
